# ADR-002: Per-PID cache-aligned BPF_MAP_TYPE_RINGBUF for pre-image extents

## Status
Accepted

## Context

Suspect write pre-image extents must be diverted into a lightweight,
zero-copy storage mechanism that the Go userspace daemon can consume
without full-file copies or blocking the write path.

Constraints:
- One ring buffer per PID (keyed by tgid) so per-process telemetry is
  isolated and bounded.
- Cache-aligned (64-byte) extent descriptor to avoid false sharing.
- `BPF_MAP_TYPE_RINGBUF` for lock-free, multi-producer/single-consumer
  semantics.
- Fixed maximum extent size (64 KiB) to bound memory per diverted write.
- Ring buffer sized to accommodate ransomware write bursts (4 MiB).

Options Considered
1. **BPF_MAP_TYPE_PERF_EVENT_ARRAY** — per-CPU, higher overhead, less
   suitable for bulk extent payloads.
2. **BPF_MAP_TYPE_RINGBUF (global, single)** — simpler but contends
   across PIDs; no per-process isolation.
3. **BPF_MAP_TYPE_LRU_HASH + userspace mmap** — complex synchronization,
   not zero-copy for the payload.
4. **Per-PID BPF_MAP_TYPE_RINGBUF** — isolated, bounded, lock-free,
   cache-aligned descriptors.

## Decision

Use one cache-aligned `BPF_MAP_TYPE_RINGBUF` per PID (keyed by tgid),
pinned via `LIBBPF_PIN_BY_NAME` for zero-copy consumption by the Go
daemon. Divert suspect pre-image extents (up to 64 KiB) directly into the
ring buffer.

## Consequences

### Positive
- Lock-free, zero-copy handoff between kernel and userspace.
- Per-PID isolation bounds memory and simplifies containment per process.
- Fixed extent size caps worst-case memory per ring buffer.

### Negative
- Ring buffer overflow requires an eviction policy (most-recent
  descriptors preserved).
- 64 KiB max extent means larger writes are truncated or split across
  multiple descriptors.

## Revisit When

Ring-buffer overflow under sustained ransomware bursts becomes
measurable; consider spillover to a per-PID BPF hash map or a secondary
overflow ring.
